业务案例 / 翻单决策中心

01 / AI 辅助业务决策系统

让翻单不只依赖经验，
而是一条可追溯的决策链路。

面向服饰电商补货场景，统一商品、销量、库存、相似款与翻单系数，帮助商品团队定位需要翻单或持续关注的商品，并解释建议从何而来。

项目速览
角色
需求发现 · 产品设计 · 数据库与开发 · 上线推广
技术
Node.js · SQL Server · T-SQL · Excel
用户
商品团队 · 运营团队
状态
内部日常使用 · 持续迭代
问题

信息分散，判断容易遗漏

翻单需要同时查看商品资料、渠道销量、库存、历史参考款和业务系数。信息散落在多个表和人工 Excel 中，商品人员需要重复查找、比对和计算，也难以保证每次判断口径一致。

目标

把“怎么判断”变成产品规则

系统不是简单罗列库存，而是先预估需求，再匹配业务系数、计算库存缺口和优先级，最后形成需翻单与持续关注两个视图，让商品人员基于统一结果复核与执行。

秒级查询 大数量场景下，页面打开、查询和销量计算从约 1 分钟以上缩短到秒级
统一口径 销量、系数、预测需求和库存缺口沿同一条规则链路生成
可追溯 支持运行快照、版本校验、刷新日志和 Excel 导入审计
产品设计

一个决策系统，三层使用体验

01 · 商品工作人员先看结果

翻单池优先呈现需要处理的商品，持续关注池承接暂不翻单但值得跟踪的款式，减少在整张数据表中寻找异常项的成本。

02 · 业务负责人管理规则

系数库、规则配置和相似款关联把经验显性化；Excel 导入包含预检、差异下载、确认写入与审计，避免规则被无痕修改。

03 · 技术和运营定位问题

通过 traceId、refreshId、分阶段日志和运行快照，区分数据库、计算和运行结果发布环节的耗时与异常。

工程落地

业务系统也需要可靠边界

  • 支持读、写、管理员三级权限和现有 Acme 登录鉴权。
  • 适配嵌入现有业务系统与 /fandan/ 子路径部署。
  • 加入运行快照、版本校验、缓存恢复和异步重建。
  • 使用有界 Worker 与批处理控制大数据量任务。
  • 提供独立 Mock 模式，便于无数据库和鉴权环境演示。
上线迭代

先被使用，再继续完善

首版上线后，根据商品团队反馈补充拒退率计算、历史拒退分析和标签 Excel 导入。通过每周 OKR 汇报项目进度，并与 IT 部门完成数据库账户、业务数据接入和云端部署对接。

需求发现 业务规则 数据库 产品开发 测试 跨部门上线
真实边界

系统提供决策建议，最终动作仍由商品人员确认

翻单系数来源于业务配置，预测结果依赖输入数据与历史参考关系。系统当前的目标是降低信息遗漏和重复判断，而不是替代商品人员对款式、渠道和经营策略的综合判断；Mock 模式只用于演示，不代表正式业务数据。
